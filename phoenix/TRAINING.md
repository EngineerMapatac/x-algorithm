# Training the Phoenix recsys model

This export includes a runnable, single-host training path for the ranking and
retrieval models. [`QUICKSTART.md`](QUICKSTART.md) is the tested way to generate
synthetic data, train both nano configs, write checkpoints, resume, and serve
them.

The shipped path is an offline verification harness. It does not include
production data feeds, production checkpoints, multi-host orchestration, or a
production-scale recipe. Supply those parts for your own deployment.

## Optimizers and training step

Two dense-parameter optimizer families ship in this export:

- **Muon** (`xrex/optimizers/recsys/muon.py`): the production home-ranker
  recipe — consistent-RMS scaling with decoupled weight decay on the matrix
  and embedding partitions. The flagship ranking configs and
  `home_direct_packed_nano` select it (`optim="muon"`), so the nano trains
  with the same dense-optimizer recipe production runs.
- **Standard Optax AdamW**: the slot used by the remaining shipped configs
  (two-tower retrieval, gen-recs, and the legacy ranking presets). The
  internal deployment uses a tuned RMS-normalized-Adam derivative in that
  slot; AdamW is the validated equivalent for those released recipes, and
  every config on that slot trains with it end to end.

Embedding tables use a separate sparse rowwise AdaGrad optimizer; the ranking
flagship recipe (and the nano) additionally runs it with accumulator
half-life decay, lazy per-row decay, and decoupled weight decay. At a high
level, each step:

1. looks up and deduplicates the embedding rows used by the batch;
2. computes the loss and gradients for dense parameters and embeddings;
3. applies the config's dense optimizer to dense parameters and rowwise
   AdaGrad to the referenced embedding rows; and
4. skips updates when gradients are non-finite.

The runnable reference implementation is
[`reference/train_step.py`](reference/train_step.py). Model losses are defined
under `xrex/models/`, and the optimizers under `xrex/optimizers/`.

## Data

The public launcher reads a finite offline Parquet dump generated by
`reference/dump_gen.py`. Ranking and two-tower retrieval use the same dump.
Semantic-ID snapshots are generated by `reference/world_snapshots.py`.

Use the data commands in [`QUICKSTART.md`](QUICKSTART.md); in particular,
generate snapshots first and pass the generated SID parquet to `dump_gen.py`.
The launcher reads the partition count from `.valid_batches.json` and points the
selected config at the dump.

The synthetic data is deterministic for a fixed seed and contains no production
data. It is intended to verify mechanics, not model quality.

## Run training

The launcher defaults to the nano ranking config:

```bash
uv run python reference/train_synth.py \
  --data ./synth_dump --steps 6 --out "$PWD/checkpoints" --metrics
```

For two-tower retrieval:

```bash
uv run python reference/train_synth.py \
  --config xrecsys_two_tower_nano_offline_kafka_dump \
  --data ./synth_dump --steps 6 --out "$PWD/checkpoints"
```

Run `uv run python reference/train_synth.py --help` for the launcher options.
The launcher is single-GPU, clamps the requested steps to the finite dump's
capacity, and writes periodic and final checkpoints.

With `--metrics`, per-step metrics including `loss` are written to:

```text
<out>/run/metrics.jsonl
```

The synthetic ranking rehearsal showed decreasing loss, but that result is only
a check that training runs. It is not a quality or convergence claim.

## Checkpoints and resume

Checkpoints are written under:

```text
<out>/<config_name>/elapsed_samples_<n>/<run_id>/
```

To resume, run the launcher again with the same `--out` and a larger `--steps`
value. The trainer restores model state, optimizer state, and the data position
from the newest checkpoint. The dump is finite, so generate more rows before a
longer schedule.

The serving example in [`QUICKSTART.md`](QUICKSTART.md) loads a checkpoint
written by this launcher. No pretrained checkpoint is included.

## Production use

For a production-scale deployment, provide your own:

- data source and data lifecycle;
- multi-host scheduling and orchestration;
- model configuration, training schedule, evaluation, and monitoring; and
- checkpoint storage and serving integration.

The nano synthetic harness does not establish production accuracy,
throughput, reliability, or scale.
